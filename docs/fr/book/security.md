# Sécurité

Voici chaque menace du Top 10:2025 de l'OWASP (la liste des dix risques les plus graves des applications web, que
tient la fondation OWASP), et les autres que rencontre une app (l'application, le serveur et ses pages) faite de
comptes et de tenants (un tenant : un client de la plateforme, comme un cabinet ou une entreprise, avec ses données à
lui). Pour chacune : la défense de Centauri, active par défaut, et le test qui la prouve. Les tests sont dans
`src/app/app.test.ce` (app), `tests/auth.test.ce` (auth), `tests/apptest.test.ce` (apptest) et
`examples/invoices/tests/invoices.test.ce` (invoices).

| menace | défense | test |
|---|---|---|
| **A01** broken access control (un contrôle d'accès cassé) : les données d'un autre lues ou changées par leur id (IDOR, l'insecure direct object reference) | le rôle sur l'endpoint (une adresse de l'API avec sa méthode HTTP, comme `POST /clients`) : 401, 403 ; le tenant tiré de `r.User`, jamais de la requête ; `app.Own` (404, jamais 403) ; la sortie à travers sa forme (ce qu'une valeur doit être : un texte de 1 à 120 octets, un nombre entier...) | `apptest.Isolated` sur chaque endpoint, et lui qui attrape une route (un endpoint et la fonction qui y répond) sans `app.Own` (apptest `isLeakCaught`) ; invoices `isOfficesApart`, `isAccountantSeesInvoicesOnly` ; app `isMadeOwnedAndNumbered` |
| des rôles élevés par quelqu'un qui ne les a pas | personne ne donne ni ne retire un rôle qu'il n'a pas ; un tenant garde toujours un owner (un propriétaire) ; un rôle mal écrit dans un contrat (ce qu'un endpoint prend, ce qu'il rend et le rôle qu'il demande, lu par le serveur et par les pages) arrête le démarrage | auth `isNoRaiseOfOwnRoles` ; app `isRoleWrittenWrongRefused`, `isRoleChecked` |
| des champs qui fuient (API3:2023), ou qu'un expéditeur ajoute | `check.Out` n'envoie que les champs déclarés ; `check.Read` laisse tomber les autres | app `isOutputFilteredAndErrorsHidden`, `isMadeOwnedAndNumbered` ; std/check `isInvoiceRead` |
| **A02** security misconfiguration (une sécurité mal réglée) | trois profils fixes (un profil est une manière de lancer l'app : dev, test ou prod) ; prod refuse de démarrer sans https, sans secret et sans base de données, et nomme chacun ; des headers (des lignes d'information en tête d'une réponse) sur chaque réponse ; ni OpenAPI (le format standard qui décrit une API HTTP) ni détail des erreurs en prod | app `isSecurityHeaders`, `isOpenApiInTestOnly`, `isOutputFilteredAndErrorsHidden` ; l'exemple de `Read` en prod |
| **A03** supply chain (la chaîne d'approvisionnement : le code d'autres projets que l'app embarque) | aucun paquet venu d'autres : Centauri, Cesia, Cepheus sont les nôtres ; `deps/` vérifié fichier par fichier par `cesia.lock` ; libsodium et OpenSSL, fuzzés par leurs projets (le fuzz : un test qui envoie en masse des entrées tirées au hasard ou cassées) | Cesia refuse un fichier dont l'empreinte diffère de celle de `cesia.lock` |
| **A04** cryptographic failures (des erreurs de cryptographie) | Argon2id (la fonction qui calcule l'empreinte d'un mot de passe) ; le BLAKE2b des secrets des sessions (une session : le temps où un utilisateur reste connecté), comparé en temps constant (la durée de la comparaison ne trahit pas où les textes diffèrent) ; les curseurs (la marque d'où reprend la page suivante d'une liste) scellés (chiffrés et authentifiés, par XSalsa20-Poly1305) sous une clé pour chaque endpoint et chaque tenant, les challenges (les défis que le navigateur doit résoudre) sous HMAC-SHA-256 ; le hasard du noyau ; aucun algorithme choisi par le client (pas de JWT, les JSON Web Tokens) | auth `isNoSecretKept`, `isForgedCookieNobody` ; app `isPagedBySealedCursors`, `isCursorOfBeforeRead` |
| **A05** injection (des données reçues qui deviennent du code) | une question à Cepheus est une structure, ses valeurs ne sont jamais du code ; du JSON en entrée, du JSON en sortie ; une cellule de CSV qui commence par `=`, `+`, `-`, `@` reçoit un `'` devant | `apptest.Fuzz` avec du SQL, du HTML et des formules ; invoices `isCsvOfTheFilter` |
| **A06** insecure design (une conception qui n'est pas sûre) | des écritures avec `Expect`, des numéros avec `Incr` dans le groupe (un groupe : des écritures faites toutes ensemble, ou pas du tout), `unique` ; aucune transaction ouverte entre deux requêtes ; un GET ne fait que lire | invoices `isPaidOnceAtTheSameMoment`, `isNumberedInOrderAtOnce` ; app `isGetThatWritesRefused` |
| **A07** authentication failures (des erreurs d'authentification) | des sessions coupées en deux, `__Host-`, `HttpOnly`, `SameSite=Strict`, une nouvelle à chaque connexion ; les échecs comptés, et des délais qui doublent ; la même réponse, dans le même temps, pour un identifiant inconnu ; des sessions qui prennent fin ; une déconnexion pour de bon ; les sessions qu'un processus garde (`APP_SESSION_CACHE`, 2 s), gardées sous le BLAKE2b de leur cookie (un petit texte que le navigateur garde et renvoie à chaque requête), oubliées tout de suite par une écriture des comptes faite dans ce processus ; ailleurs, l'écriture est vue en moins de ces secondes | auth `isLockedAfterFailures`, `isUnknownLoginAnsweredAsAWrongPassword`, `isSignedOutForGood`, `isSessionIdleAndOld`, `isForgedCookieNobody`, `isPasswordChanged`, `isDisabledBySuper`, `isRoleTakenSeenAtOnce`, `isChangeOutsideSeenWithinSessionCache`, `isForgedCookieNobodyBesideAKeptOne` |
| **A08** integrity failures (des données acceptées sans vérifier leur intégrité) | aucune désérialisation d'objets (refaire des objets du programme à partir d'octets reçus) : le JSON devient des valeurs, puis passe par une forme ; un curseur ou un challenge fait à la main est refusé | app `isPagedBySealedCursors` ; invoices `isBadCursorRefused` ; auth `isProofOfWorkAsked` (forgé) |
| **A09** logging and alerting failures (des journaux et des alertes qui manquent) | chaque écriture avec qui et pourquoi (Cepheus) ; les connexions, les échecs, les blocages, les refus, les invitations, les rôles, en événements ; des métriques des refus ; aucun secret, corps, cookie ni query (la partie de l'adresse après `?`) dans un log (le journal où le serveur note ce qu'il fait) | auth `isEventsAndAdministration`, `isNoSecretKept` (les logs aussi) |
| **A10** exceptional conditions (des cas exceptionnels mal traités) | les erreurs sont des valeurs, envoyées en Problem Details (le format standard des erreurs d'une API HTTP, RFC 9457) ; une panic (un arrêt sur une erreur du programme) n'arrête que sa fiber (un fil d'exécution léger, à l'intérieur du processus) et répond un 500, sans détail en prod ; un délai pour chaque requête | `apptest.Fuzz` (aucun 500), et lui qui attrape un handler (la fonction qui répond à une requête) qui échoue (apptest `isCrashCaught`) |
| cross-site request forgery (CSRF : une requête envoyée depuis un autre site, avec le cookie de l'utilisateur) | une écriture venue d'un autre site est refusée, son cookie jamais lu ; SameSite=Strict | app `isOtherSiteRefused` ; invoices `isOtherOriginRefused` |
| déni de service (rendre le serveur incapable de répondre) | des limites par adresse (IPv6 par /64), par utilisateur, par tenant, par endpoint, une requête refusée à cause de son rôle comptée aussi ; les bornes de std/http (tête, corps, temps, mémoire) ; les hash de mots de passe (un hash : une empreinte, un nombre calculé à partir d'un texte, d'où on ne peut pas revenir au texte) calculés dans un nombre borné de places ; les événements de refus écrits une fois par minute et par clé ; les tables des limites et des sessions gardées bornées, élaguées avec un quart de marge, pour qu'un flot de nouvelles adresses ou de nouveaux cookies n'élague jamais à chaque requête | app `isLimited`, `isFloodOfKeysPrunedWithRoom`, `isFloodOfSessionsBounded` ; auth `isSignUpLimitedByAddressAndTenantsByHour` |
| les bots (des programmes qui se font passer pour des visiteurs) | la preuve de travail (proof of work : un petit calcul que le navigateur doit faire avant d'envoyer, qui coûte cher à un robot) sous attaque, chaque réponse ne servant qu'une fois ; le champ piège ; les nouveaux tenants plafonnés par heure | auth `isProofOfWorkAsked`, `isProofOfWorkUnderAttack`, `isBotTrapped`, `isSignUpLimitedByAddressAndTenantsByHour` |
| le vol d'un token (un jeton : un texte secret qui prouve un droit) | aucun token dans la page ; le cookie illisible pour un script ; une session terminée l'est tout de suite dans son processus, et en moins de `APP_SESSION_CACHE` secondes (2) dans les autres workers (les processus de l'app) | auth `isSignedOutForGood`, `isSessionsListedAndEnded`, `isChangeOutsideSeenWithinSessionCache` |
| une API qui casse (*never break user space* : ne jamais casser ce qui marche chez ceux qui s'en servent) | la surface (ce sur quoi les clients de l'API comptent) comparée à chaque test | `apptest.Surface`, et lui qui attrape ce qui casse (apptest `isSurfaceKept`) |

un partenaire quand quelque chose arrive. Chaque menace a son test dans `tests/jobs.test.ce`, `tests/mail.test.ce`,
`tests/checks.test.ce`, `tests/files.test.ce`, `tests/live.test.ce`, `tests/calls.test.ce`, `tests/migrate.test.ce`,

Ce que Centauri ne fait pas encore : le troisième mur, un token de Cepheus par rôle qui ne lit que ses kinds (G16 ; un
kind : une sorte de chose dans la base de données, comme les factures ou les clients), pour les rôles qui ne doivent
jamais voir certains kinds (un comptable extérieur) ; la vérification d'un nouveau mot de passe contre les listes de
mots de passe qui ont fuité. La réponse neutre d'une inscription est venue avec L2 (`SignUpAnswer`, avec le courrier) ;
l'authentification à plusieurs facteurs et les passkeys (L3) sont faites maintenant : TOTP et codes de secours,
passkeys, connexion par un fournisseur, et le second facteur sur chaque voie d'entrée.
